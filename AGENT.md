# Agent handover

Read this first if you are an AI coding agent (Claude Code or similar) picking up Vabbit.
It records what the project is, how to work on it, and the decisions the owner already
made, so you don't re-ask or undo them. Open work is in [BACKLOG.md](BACKLOG.md).

## What Vabbit is

A small WireGuard mesh VPN. The control plane is one Bunny.net Edge Script per network;
devices run one static Go binary. Think "self-hosted Tailscale/NetBird with a serverless
control plane". Repo: `github.com/thomaskhub/vabbit` (branch `main`). The project was first
called EdgeGuard; the owner renamed it Vabbit. Don't reintroduce the old name, and don't
mention or compare to NetBird in the docs (removed on purpose).

| Part | Path | Language | Notes |
|---|---|---|---|
| Control plane | `edge/` | TypeScript (Bun) | `src/handler.ts` API, `store.ts` Bunny Storage, `ipam.ts`, `crypto.ts`, `dev.ts` local server; `worker.ts` + `r2store.ts` run the same API as a Cloudflare Worker on R2 (manual deploy, docs/DEPLOY.md) |
| Client + agent | `client/` (module `vabbit`) | Go | `cmd/vabbit`, `adminlogin/` (encrypted admin file), `internal/{agent,api,relay,state,stun,wg}` |
| Deploy (`vabbit deploy`) | `client/internal/deploy/` | Go | `cli/` (the subcommand), `config/`, `bunny/` (API client), `edgescript/` (embeds the built edge script); was a separate `vabbit deploy` binary until 2026-10-08 |
| Installer | `scripts/install.sh`, `scripts/install.ps1` | POSIX sh, PowerShell | one-liners for Linux and Windows devices |
| Packaging | `packaging/vabbit@.service` | systemd | `vabbit@<iface>`; only CAP_NET_ADMIN + CAP_NET_BIND_SERVICE |
| Docs | `README.md`, `docs/DESIGN.md`, `docs/DEPLOY.md` | | README is the user guide, organised by role |
| SBOM | `sbom/` | CycloneDX | generated by `scripts/sbom.sh`, checked in CI |

There is no database: state is small JSON files in a private Bunny Storage zone
(`devices/<id>.json`, `setup-keys/<sha256>.json`). See `docs/DESIGN.md` for the full design.

## How it works (short)

- **Tokens:** admin (`vba_…`), setup key (`vbk_…`), device (`vbd_<id>.<secret>`). All 256-bit
  random; the server stores only SHA-256 hashes and compares in constant time. The admin
  token's hash is the edge script secret `ADMIN_TOKEN_SHA256`; the hash exists so the real
  token is never stored at Bunny.
- **Devices** enroll with a setup key, keep their WireGuard private key locally, sync every 15s.
- **NAT traversal:** STUN on the WireGuard socket, both sides punch; peers get a `/32` only
  once a direct handshake is fresh, otherwise traffic goes via the hub.
- **Hubs:** devices with a public endpoint that the **admin** marks as hub
  (`vabbit devices set <id> --hub=true`, or `vabbit up --hub` when the admin is logged in on
  that machine). Devices can never promote themselves because a hub sees relayed traffic.
  A hub also serves TLS on TCP 443 for UDP-blocked networks (cert fingerprint pinned via the
  control plane).
- **Backup hubs:** several hubs allowed. Each device uses the oldest live hub; if it receives
  nothing from it for 40s (`hubDeadAfter`, `client/internal/agent/hubs.go`) it moves to the
  next live one and stays there (sticky, no flapping). Other hubs are treated as ordinary peers.

## Admin flow (one flow, few flags)

The owner insisted on **one deploy flow with as few flags as possible**; the person who
deploys is assumed to be the admin.

1. `vabbit deploy init` writes `vabbit.toml` (never overwrites an existing one), asks for a
   new master password (masked with `*`, min 8 chars, typed twice), and creates an admin
   token per network in `~/.config/vabbit/admin.json`.
2. `BUNNY_API_KEY=… vabbit deploy apply` asks for the master password, deploys each token's
   hash, saves each network's URL into `admin.json`, waits until the network is healthy.
   It refuses if a network already has an admin token that `admin.json` doesn't hold
   (copy the file from the other admin, or `rotate-admin`).
3. `vabbit` admin commands (`keys`, `devices`, …) then just work: they read `admin.json`.

Other commands: `plan` (no password), `rotate-admin -n NAME`, `destroy -n NAME --yes`
(also drops the entry from `admin.json`). Remaining deploy flags: `-f`, `-n`,
`--allow-cidr-change`, `destroy --yes`.

`admin.json`: the whole `{networks:[{name,server,token}]}` sealed with Argon2id (t=3,
64 MiB, 4 threads) + XChaCha20-Poly1305, AD `vabbit-admin-login-v1`, mode 0600 in a 0700
dir; under sudo the path follows `SUDO_USER`. Env: `VABBIT_ADMIN_PASSWORD` (non-interactive),
`VABBIT_NETWORK` (pick a network when there are several). More admins = share `admin.json`
and send the password separately. `vabbit login --server URL` adds a token (prompted
masked or from stdin) for manual setups; `vabbit logout` asks you to type `yes`.

## Users and installer

```sh
curl -fsSL https://raw.githubusercontent.com/thomaskhub/vabbit/main/scripts/install.sh | \
  sudo VABBIT_SERVER=https://… VABBIT_SETUP_KEY=vbk_… sh
```

`install.sh` downloads release assets (`vabbit-linux-{amd64,arm64}`, `vabbit@.service`,
`SHA256SUMS`), verifies checksums, installs to `/usr/local/bin`, and with a server and key runs
`vabbit up --dry-run` then `systemctl enable --now vabbit@IFACE`. Env: `VABBIT_VERSION`,
`VABBIT_SERVER`, `VABBIT_SETUP_KEY`, `VABBIT_NAME`, `VABBIT_ENDPOINT`, `VABBIT_IFACE`,
`GITHUB_TOKEN` (private repo), `VABBIT_REPO`, `VABBIT_BASE_URL` (tests).

Windows: `irm …/scripts/install.ps1 | iex` as Administrator (same env vars) installs
`vabbit.exe` + `wintun.dll` to `C:\Program Files\Vabbit` and runs `vabbit service install`
(service `vabbit-<iface>`, state and `vabbit.log` in `C:\ProgramData\vabbit`, DACL SYSTEM +
Administrators via `internal/secfile`). Platform code: `client/internal/wg/netcfg_windows.go`,
`client/cmd/vabbit/platform_windows.go`. CI job `windows` runs `scripts/windows-smoke.ps1`.

macOS: the same `install.sh` installs `/usr/local/bin/vabbit` and runs `vabbit service install`
(launchd `com.vabbit.<iface>`, plist in `/Library/LaunchDaemons`, log `/var/log/vabbit-<iface>.log`,
state in `/var/db/vabbit`). The interface is `utunN` (`Device.IfName()`); vabbit's own name (`vb0`)
names the control socket `/var/run/wireguard/vb0.sock`. Code: `client/internal/wg/netcfg_darwin.go`,
`client/cmd/vabbit/platform_darwin.go`. **CI minutes:** the owner has 2,000 a month; macOS costs 10x,
Windows 2x. So `macos.yml` is manual only (dispatch it once per real macOS change), and
`windows.yml` only runs when client code or Windows scripts change.

Releases: pushing a `v*` tag runs `.github/workflows/release.yml` (client linux
and darwin amd64/arm64 with `-X main.version`, unit file, install.sh,
SHA256SUMS, `gh release create --generate-notes`). Tags with a suffix (`-rc.1`) become
pre-releases. The workflow can also be run by hand with a `tag` input, which creates the tag;
agent sessions use that (`POST /repos/thomaskhub/vabbit/actions/workflows/release.yml/dispatches`)
because they can't push tags. Published so far: `v0.1.0-rc.1` to `rc.4` (pre-releases; rc.3 has PRs 1-5 and `vabbit deploy`, rc.4 the Windows client).

## Working on the code

```sh
make test                         # edge bun test + go vet/test for client and deploy
make build                        # dist/vabbit (embeds edge/dist for vabbit deploy)
sudo ./scripts/e2e-nat.sh         # real tunnels in network namespaces: cone, symmetric, hotel, failover
./scripts/sbom.sh                 # regenerate sbom/ after any dependency change, then commit it
cd edge && ADMIN_TOKEN_SHA256=<hash> bun run dev   # local control plane on :8787
```

- CI (`.github/workflows/ci.yml`): edge typecheck/test/build; client gofmt/vet/test +
  shellcheck of `install.sh`; deploy vet/test/build; SBOM must match (`git diff --exit-code
  sbom/`); e2e as root. Keep it green on every push.
- `e2e-nat.sh` needs root and leaves `eg-*` namespaces behind if killed; delete them before
  rerunning. Its failover mode kills the first hub with `pkill -f -- "--iface eghub --state-dir"`;
  never run a `pkill -f` whose pattern appears in your own command line.
- `scripts/sbom.sh` strips `GOVERSION` and the replace-module hashes so the SBOM is the same on
  every Go version; the local `vabbit` module is labelled MIT.
- After changing `edge/`, `make client` copies the bundle into `client/internal/deploy/edgescript/bundle/`.

## Conventions and owner preferences

- Plain, short docs aimed at users; one source of truth (don't duplicate README content in
  `docs/`). Use-case diagrams are SVGs in `docs/use-cases/`; keep them in sync with commands.
- Fewer flags over more options; secure defaults; no secrets on the command line or in files
  in clear text.
- Commits go straight to `main` when the owner asked for the change; CI must pass. Ask before
  anything public or irreversible (releases, repo visibility, deleting things).
- Config format is TOML (owner preferred YAML at first but accepted TOML, as Wrangler uses it).
- Licence MIT (permissive and simple; no patents involved; all dependencies are open
  standards/licences, see `sbom/`).
- Logo: the owner's Gemini-made rabbit, traced to SVG (`docs/brand/`). The owner rejected
  hand-drawn bunnies; don't redraw it.

## Decision log

| Decision | Why |
|---|---|
| Bunny Edge Script as the whole control plane, Storage JSON instead of a DB | Serverless, tiny, cheap; one script = one network |
| Hash of the admin token at Bunny | Real token never stored at Bunny |
| TOTP dropped | Logins are also used by servers/automation, so a second factor doesn't fit one unified flow |
| TOML config | Like Wrangler; owner fine with it |
| Name Vabbit, NetBird references removed | Owner's choice |
| MIT licence | Permissive, simple |
| Admin login encrypted with a master password | No clear-text token on the admin laptop |
| One deploy flow (`init`, `apply`), `--token-file` / `--admin-login-file` and similar flags removed | Owner: "too many flags" |
| Admin decides hubs, can change any time; "hub key" idea rejected | Hubs see relayed traffic, so only the admin promotes them |
| Several hubs with automatic failover | Owner wanted a backup hub |
| One-line installer from GitHub raw + tagged releases | Easy client setup |
| macOS devices: utun + launchd, hubs stay Linux-only; macOS CI by hand only | Owner pays for CI minutes and macOS runners cost 10x |
| Windows devices: Wintun + a Windows service, hubs stay Linux-only | Owner can test Windows; forwarding/NAT on Windows is a different world, so hubs are not ported |
| `vabbit-deploy` merged into `vabbit` as `vabbit deploy` | One program to install and explain; gives Mac admins a `vabbit` build. Deploy code on devices is harmless: it needs the Bunny API key |
